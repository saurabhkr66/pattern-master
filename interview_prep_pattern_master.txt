# EXHAUSTIVE INTERVIEW QUESTION GUIDE: PATTERN MASTER
====================================================================
This document contains a highly detailed breakdown of every potential interview question an SDE (Software Development Engineer) interviewer might ask regarding the "Pattern Master" project. It covers Frontend, Backend, Database Design, Algorithms, and System Design scalability.

---

## 1. FRONTEND ARCHITECTURE & REACT
--------------------------------------------------------------------

**Q1: How did you manage the state of a 3-hour long exam containing 200 questions without crashing the browser or causing massive re-rendering lags?**
**Answer:** 
- **Decoupled State**: I split the state into logical chunks rather than a single monolithic object. `mcqSelected`, `msqSelected`, `natValues`, and `statuses` (flagged, answered) are separate dictionaries.
- **Minimizing Re-renders**: Instead of updating the parent component every second to track the time spent on *each* individual question, I utilized `useRef` to store the `currentQId`. The `setInterval` function references `currentQIdRef.current` to increment the time for the active question inside a generic `timeSpent` dictionary state, ensuring the actual question rendering components don't unnecessarily re-render every second.
- **Memoization**: I used `useMemo` for filtering operations (like the search and filter tabs in the Analysis view) and `useCallback` for functions like `buildAnswers` and `loadAnalysis` to prevent child components from re-rendering unnecessarily.

**Q2: A standard `setInterval` in JavaScript can suffer from "drift" over a 3-hour period due to the single-threaded event loop and background tab throttling. How do you handle this?**
**Answer:**
While a basic `setInterval` works for the UI timer countdown, browsers heavily throttle intervals when the tab is inactive (e.g., dropping to 1 execution per minute). 
*Current Implementation:* We decrement `timeLeft` every second.
*Better Scalable Approach (to discuss in interview):* We should record a `startTime` timestamp when the test begins. Inside the interval, calculate `TimeLeft = TotalDuration - (Date.now() - startTime)`. This completely eliminates event loop drift and background tab throttling issues.

**Q3: How did you securely render third-party or scraped LaTeX/Math equations?**
**Answer:**
I built a custom `MathRenderer` component utilizing `react-markdown` and `rehype-katex`. Because scraped data is inherently dirty, I injected a custom regex pre-processing layer before rendering. It normalizes smart quotes, replaces standalone Unicode math symbols (like `∵` or `⇒`) with proper LaTeX commands (`\because`, `\Rightarrow`), and wraps pseudo-fractions `{A}/{B}` into `\frac{A}{B}`. This ensures the app doesn't crash on invalid KaTeX syntax and prevents XSS vulnerabilities since ReactMarkdown sanitizes raw HTML by default.

## 2. BACKEND API & NEXT.JS
--------------------------------------------------------------------

**Q1: How did you design the API for submitting a test? Walk me through the payload and logic.**
**Answer:**
The `/api/test/submit` endpoint receives a POST request.
- **Payload**: `answers` array (containing `questionId`, `userAnswer`, `timeSpentSecs`, etc.), `timeTakenSecs`, and the `mockTestId`.
- **Validation**: Verifies the user using Clerk auth. 
- **Retrieval**: Fetches the `MockTestTemplate` using the `mockTestId`.
- **Grading Engine**: Iterates through the answers. It checks the `questionType` (MCQ, MSQ, NAT). It applies positive marks for correct answers and dynamically applies negative marking (e.g., -1/3 for GATE, -0.25 for JEE). 
- **Section B Logic**: For exams like JEE/NEET, there are "optional" sections (e.g., attempt 10 out of 15). The loop uses a Map to track how many optional questions have been answered per section, and strictly ignores any answers beyond the limit `countSize`.

**Q2: What is caching like in Next.js App Router for this project?**
**Answer:**
After a test is submitted, the user's dashboard needs to reflect the newly completed test. Next.js aggressively caches pages. I used `revalidatePath("/dashboard", "page")` and `revalidateTag("dashboard")` at the very end of the submit API route to purge the cache and ensure the user instantly sees their updated scores and history upon redirection.

## 3. DATABASE DESIGN & PRISMA (DATA MODELING)
--------------------------------------------------------------------

**Q1: I notice you use JSON fields for `questions` inside `MockTestTemplate` and `answers` inside `TestSession`. Why use JSON in a relational PostgreSQL database instead of normalized tables (e.g., `TestSessionQuestionMapping`)?**
**Answer:**
This was a deliberate design choice based on two principles: **Point-in-Time Snapshotting** and **Read Optimization**.
1. **Snapshotting**: Exam patterns, options, or explanations might be updated by admins later. If a user reviews a test they took 6 months ago, they should see the exact test *as they took it*. Storing the JSON payload guarantees immutability for that session.
2. **Performance (Avoiding N+1)**: A mock test has 200 questions. If normalized, fetching a test would require fetching 1 `TestSession`, 200 `SessionAnswer` rows, and joining 200 `GeneratedQuestion` or `PYQ` rows. By utilizing a JSON field, the entire 200-question breakdown is fetched in a single, blazing-fast I/O operation.

**Q2: How did you handle backward compatibility when adding new features, like the "Topic" categorization field?**
**Answer:**
Recently, an AI engine was added to tag questions with specific `topic` names. However, old `TestSession` JSON snapshots didn't have this field. Instead of writing a complex migration script to update thousands of old JSON blobs, I implemented an on-the-fly reconciliation pattern in the `GET` history API. If an old session lacks the topic, the server fetches the related `MockTestTemplate`, extracts the modern topics, and dynamically merges them into the old session payload before sending it to the client.

**Q3: What indexing strategies did you use?**
**Answer:**
To speed up dashboard queries and analytics, I used compound indexes. For example, in the `Attempt` model (which tracks every single question ever answered by a user), I added `@@index([user_id, is_correct, created_at(sort: Desc)])`. This allows the DB to instantly answer analytical queries like "Give me the last 50 questions this user got wrong."

## 4. ALGORITHMS & BUSINESS LOGIC
--------------------------------------------------------------------

**Q1: Explain how you grade NAT (Numerical Answer Type) questions?**
**Answer:**
NAT questions don't have exact string matches. I implemented a parsing utility `checkNat()`. 
- First, it parses the user's string into a float.
- It checks if the correct answer string contains a range indicator like `:` (e.g., `10.5:11.5`) or the word `to` (e.g., `10.5 to 11.5`).
- It splits the string, extracts the `min` and `max` floats, and evaluates `val >= min && val <= max`.

**Q2: I see a `Flashcard` model in your schema. How does the learning algorithm work?**
**Answer:**
It implements the **SuperMemo-2 (SM-2)** spaced repetition algorithm.
Each flashcard tracks `interval` (days until next review), `ease_factor` (multiplier starting at 2.5), and `repetitions` (consecutive correct answers).
When a user reviews a card, they give it a grade (e.g., 0 to 5).
- If grade >= 3 (Correct): `repetitions` increments. The new `interval` is calculated by multiplying the previous interval by the `ease_factor`. The `ease_factor` is then adjusted up or down based on the exact grade.
- If grade < 3 (Wrong): `repetitions` drops to 0, the `interval` resets to 1 day, ensuring the user sees the card again immediately.

## 5. SYSTEM DESIGN & SCALABILITY (System Design Round)
--------------------------------------------------------------------

**Q1: Imagine an All-India Mock Test event. 100,000 students will start the test at exactly 10:00 AM, and submit at exactly 1:00 PM. How do you scale Pattern Master to handle this?**
**Answer:**
This presents two massive spikes: a **Read Spike** at 10:00 AM and a **Write Spike** at 1:00 PM.
*   **Handling the 10:00 AM Read Spike (Test Start)**:
    - **Edge Caching/CDN**: The `MockTestTemplate` (the questions payload) is identical for everyone. I would cache this JSON payload at the Edge (Cloudflare/AWS CloudFront) or in a Redis cluster. The database should receive almost zero traffic during the start of the test.
*   **Handling the 1:00 PM Write Spike (Test Submission)**:
    - **Decoupling via Message Queues**: If 100,000 users hit the `/api/test/submit` PostgreSQL endpoint simultaneously, the database connections will exhaust, and transactions will fail.
    - Instead of directly writing to Postgres, the API will push the submission payload (User ID, Answers, Time Taken) into a Message Broker (like **Apache Kafka** or **AWS SQS**).
    - The API immediately responds to the user with a `202 Accepted: "Test Submitted. Results calculating..."`.
    - Background worker nodes consume the queue at a controlled rate, performing the heavy grading logic and safely inserting the `TestSession` and `Attempt` rows into PostgreSQL without overloading it.
    - The client uses Long-Polling or Server-Sent Events (SSE) to wait for the worker to finish and redirect them to the analysis page.

**Q2: What happens if a user's laptop dies or internet disconnects at 2 Hours 50 Minutes into the test?**
**Answer:**
Currently, state is held in React memory. To make it fault-tolerant:
- Implement an auto-save mechanism. Every 60 seconds, or every time a user changes an answer, dispatch an asynchronous payload to a fast in-memory store like **Redis**.
- The payload would look like `SETEX session:{userId}:{mockId} 14400 "{current_answers_json}"`.
- When the user logs back in, `TestEngine.tsx` checks Redis for a saved state, hydrates the React state, and calculates the exact remaining `timeLeft` using the server clock, allowing them to resume seamlessly.

**Q3: How would you implement a real-time leaderboard for the mock test?**
**Answer:**
I would use **Redis Sorted Sets (ZSET)**.
When a worker grades a submission, it issues: `ZADD leaderboard:{mockTestId} {finalScore} {userId}`.
To break ties (e.g., two users get 100 marks, but User A finished in 2 hours and User B finished in 3 hours), we construct a composite score: `composite_score = actual_score + (1 - time_taken/max_time)`. 
To get a user's rank, we simply query `ZREVRANK leaderboard:{mockTestId} {userId}`, which operates in O(log(N)) time, making it lightning fast even for millions of users.
